# Server role model (Alpha 12.1)

`servers.owner_user_id` remains the sole ownership source. The owner is a member, but ownership is not a role. The Alpha 12.2 permission engine gives the owner a structural bypass.

Every server has one default `server_roles` row with `id = server_id`, `is_default = true`, and `position = 0`. Membership implies this role; no default assignment is needed. The migration backfills existing servers, and an insert trigger creates the row for new servers in the same transaction. A database trigger blocks structural changes or deletion of the default while its server exists; Alpha 12.2 permits changing its permission mask. Server deletion cascades to roles and assignments.

Custom roles have positive, unique positions within a server. **Higher position means higher role.** New roles take `max(position) + 1` while holding a lock on the server row. Gaps after deletion are valid. Future reorder operations must update positions atomically while preserving uniqueness. The role name is display data, never identity; it is trimmed, nonempty, and at most 64 characters. Role UUIDs are generated by PostgreSQL.

Assignments store only custom roles. Composite foreign keys from `(server_id, user_id)` to `server_members` and from `(server_id, role_id)` to `server_roles` prevent cross-server links and cascade on member or role removal. A unique index prevents duplicate assignments. A trigger rejects explicit default assignments; the repository also checks both relations before insertion.

Read endpoints expose `{ roles: [{ id, serverId, name, position, isDefault }] }`. They derive the actor from the server session and require membership in the requested server. The member endpoint additionally requires the target to belong to that server. Both return 404 for missing resources and inaccessible scopes. No write endpoint or permission evaluation is exposed in this slice.
