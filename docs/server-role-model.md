# Server role model (Alpha 12.1)

`servers.owner_user_id` remains the sole ownership source. The owner is a member, but ownership is not a role. The Alpha 12.2 permission engine gives the owner a structural bypass.

Every server has one default `server_roles` row with `id = server_id`, `is_default = true`, and `position = 0`. Membership implies this role; no default assignment is needed. The migration backfills existing servers, and an insert trigger creates the row for new servers in the same transaction. A database trigger blocks structural changes or deletion of the default while its server exists; Alpha 12.2 permits changing its permission mask. Server deletion cascades to roles and assignments.

Custom roles have positive, unique positions within a server. **Higher position means higher role.** New roles take `max(position) + 1` while holding a lock on the server row. Gaps after deletion are valid. Future reorder operations must update positions atomically while preserving uniqueness. The role name is display data, never identity; it is trimmed, nonempty, and at most 64 characters. Role UUIDs are generated by PostgreSQL.

Assignments store only custom roles. Composite foreign keys from `(server_id, user_id)` to `server_members` and from `(server_id, role_id)` to `server_roles` prevent cross-server links and cascade on member or role removal. A unique index prevents duplicate assignments. A trigger rejects explicit default assignments; the repository also checks both relations before insertion.

Read endpoints expose roles with canonical permission names. The server list also exposes the permission-name catalog. They derive the actor from the server session and require membership in the requested server. The member endpoint additionally requires the target to belong to that server. Both return 404 for missing resources and inaccessible scopes.

Alpha 12.4 adds `POST /servers/:serverId/roles`, `PATCH` and `DELETE /servers/:serverId/roles/:roleId`, and `PUT` and `DELETE /servers/:serverId/members/:userId/roles/:roleId`. All writes lock the server and recalculate authority inside the transaction. Creation remains owner-only because new roles are placed above every existing role. The owner may change default permissions, but not its structure or explicit assignment. Managers require `MANAGE_ROLES`; they may act only on lower roles and lower non-owner members, cannot assign themselves roles, and cannot grant permissions they do not hold or change permissions on a role assigned to themselves. The member list includes assigned custom role IDs and highest custom role position for the settings UI. Role permission changes and assignment changes request active server voice revocation after commit when the voice service is configured. A committed write returns success with `voiceRevocationPending: true` if immediate revocation fails; server voice reconciliation evicts participants whose grants exceed current permissions when the control plane recovers.

The settings UI reloads roles and members after its own writes and offers manual refresh for other sessions. Authorization on API and voice ticket issuance always reads current database state; stale controls in another tab confer no authority.
