# Cubic Desktop Preview shell

This workspace is the **11.9 Desktop Preview foundation**, not a packaged desktop release. Electron main creates one sandboxed BrowserWindow for `https://cubic.goma.ink`. The existing web service, same-origin API proxy, Socket.IO and LiveKit continue to supply the application. A future local renderer can replace the remote load target without changing account sessions or adding a privileged renderer bridge.

## Security boundary

- The remote renderer has `nodeIntegration: false`, `contextIsolation: true`, `sandbox: true`, `webSecurity: true`, `allowRunningInsecureContent: false`, and no webview or preload. There is no IPC or exposed Electron API.
- Main-frame navigation and redirects are limited to the exact Cubic HTTPS origin. External HTTP(S) destinations open in the system browser. Other schemes, malformed URLs and HTTP or alternate-port Cubic URLs are denied. New Electron windows are denied.
- Electron's default persistent Chromium session manages the ordinary Cubic HttpOnly cookie. The shell does not read, log or copy account credentials, and it does not introduce a second login system.
- Permission checks and requests require the current Cubic main frame. Explicit camera/microphone media types, speaker selection, sanitized clipboard write and fullscreen are eligible there. Display capture has a separate exact-origin policy and requires explicit source selection. Web notifications have their own exact-origin, main-document policy; filesystem and unrelated permissions remain denied.
- Certificate errors are not bypassed. The Web CSP and other response headers are not rewritten. DevTools are never opened automatically.

## Account and navigation (11.9.2)

The renderer uses Cubic's existing password login, logout and server-validated Web session. Electron's default persistent Chromium profile keeps the ordinary HttpOnly cookie across window reloads and app restarts; the shell does not access cookies, store passwords or bridge account tokens. Logout revokes the server session and clears the browser cookie through the existing Web/API flow. An expired or invalid session is handled by the Web route guard, which redirects `/app` to `/login` on the same origin. No desktop-specific authentication or session recovery is added.

The same exact-origin policy applies to normal navigation, redirects and new-window requests. Cubic routes such as `/`, `/login`, `/app`, `/verify-email`, `/reset-password` and `/invite` remain internal; external HTTP(S) links open in the system browser; unsafe schemes are denied. The shell keeps the existing single-instance window and normal in-app history. A failed network/TLS load does not downgrade to HTTP or enter a reload loop. Physical Windows smoke passed for shell, password and passkey login, session persistence, logout, navigation and external links.

## Media compatibility (11.9.3)

**Implemented policy:** Electron permission checks and requests allow ordinary `media` only for the Cubic main frame at the exact HTTPS origin and only when the requested types are explicitly `audio`, `video`, or both. Missing, unknown, and screen types are denied. Electron 44 on Windows reports `getDisplayMedia()` as `media` with `mediaTypes=[]`; a version-bound exception lets that request reach the separately secured display handler. Electron 45+ uses `display-capture` and cannot use the legacy exception. The existing `speaker-selection` permission remains origin- and main-frame-bound; output selection also depends on Chromium exposing `setSinkId` and the OS device. The remote renderer receives no device or capture API from Electron. The existing Web/LiveKit media flow is unchanged.

**Electron 44.5.1 API audit:** `setDevicePermissionHandler` applies to HID, serial and USB devices; it is not needed for microphone, camera or speaker selection. `setDisplayMediaRequestHandler` requires the application to provide a capture source. Its `useSystemPicker` option is experimental and documented for macOS 15+ only, so the Windows x64 preview uses a native Electron Menu in the main process. `desktopCapturer.getSources` enumerates screens and windows without thumbnails or icons. The menu shows names locally; only an explicitly selected source is returned to Electron. No source list, source ID, `desktopCapturer`, preload or IPC is exposed to the remote page. Closing or cancelling the menu, stale frames, source enumeration errors and concurrent requests deny capture. The callback is settled at most once.

**Screen audio:** The Web preflight currently starts with “Request shared audio” checked, so Electron's `audioRequested` flag alone does not prove the user deliberately opted in. This slice grants video only; it never requests Windows `loopback` or substitutes microphone audio. The existing Web notice reports when requested shared audio is unavailable. A separately reviewed explicit audio opt-in contract is needed before enabling system audio.

**Validated:** policy and handler tests cover explicit mic/camera types, Electron 44 compatibility, origin and frame restrictions, display eligibility, concurrent requests, cancellation and explicit source selection. Physical Windows smoke passed for mic, voice, camera, output device, screen/window selection, cancellation, repeated and concurrent requests, and real screen transmission. System audio remains unsupported.

## Notifications and Tray (11.9.4)

The main process now allows the browser's `notifications` permission only for the current Cubic WebContents, exact HTTPS origin, and main document. The Web app does **not** currently call the Web Notification API, so this policy alone does not generate native notifications. Adding notification events and preferences belongs to a later Web feature; there is no preload, IPC, DOM polling, title badge, or unread bridge. No Cubic notification sounds were added.

The main process owns one native Tray using the tracked Cubic favicon. Clicking it or choosing **Open Cubic** restores, shows, and focuses the existing window; on macOS, where closing the last window leaves the app running, it opens a window if none exists. **Quit Cubic** quits explicitly. Closing the window retains the existing lifecycle: Windows/Linux quit when the last window closes; there is no implicit close-to-tray. The Tray is destroyed during quit. Packaging copies the existing Web icon into application resources. Open/restore and Quit passed physical Windows smoke.

## Signed auto-update foundation (11.9.5)

**Configured, not released:** `electron-builder` targets Windows x64 NSIS with app ID `ink.goma.cubic.preview`, the existing Cubic `.ico`, and `forceCodeSigning: true`. Packaging copies the icon into resources so Tray still finds it. `electron-updater` reads the build-generated update configuration for the **public** `Gomaink/cubic` GitHub Releases provider and its `alpha` metadata. The remote Web renderer cannot select a feed, installer, version or update action. There is no preload or IPC. The `package:win` script always uses `--publish never`; no signing certificate, installer or published update exists yet.

Only a packaged Windows build starts the updater. It checks 30 seconds after startup and then every six hours, with one check/download at a time. A manual **Check for Updates** action in the Tray uses the same guard. Network, provider and download errors leave the Cubic window usable and log only a generic message. The updater accepts only a newer `-alpha.N` version on the current release line (for example `2.0.0-alpha.7` to `.8`); it rejects equal, older, beta, stable and other release lines. Prerelease discovery is enabled but downgrade is explicitly disabled. Once an eligible update is found, it downloads in the background. Only the updater's `update-downloaded` event enables **Restart to Update** in the existing Tray. Normal Quit never installs silently; the explicit action invokes `quitAndInstall`. No update notification is emitted in this slice.

The build uses HTTPS GitHub Releases, generated channel metadata and SHA-512 download verification from the updater stack. Before networking, the main process checks the packaged `app-update.yml` for the pinned public repo, alpha channel and a nonempty signing publisher; missing or redirected metadata disables updates. NSIS update-code-signature verification remains enabled; a signed release must have a Windows Authenticode certificate whose publisher is embedded in that configuration. **No real certificate was provided or validated in this slice.** Future release CI must receive `WIN_CSC_LINK` and `WIN_CSC_KEY_PASSWORD` only as protected secrets, validate the signed installer and metadata, and publish the installer, blockmap and alpha update metadata together as an explicit prerelease. No PAT or signing secret belongs in the app or Git. `forceCodeSigning` blocks an unsigned distributable; the local TypeScript build is not an installer. An intentionally unsigned local package would require overriding this gate and is not an auto-update candidate.

The real signed Windows build and installed A-to-B update smoke remain blockers to shipping updates. Before any publication, verify that a packaged app contains its runtime dependency and icon, that the generated feed points only to the intended public repo, and that the signature and publisher match. The library handles partial downloads, checksums and signature failures; these paths and install recovery still require installed-build Windows smoke. The update code does not fetch or run an executable itself and does not weaken TLS or Web CSP.

## Windows alpha distribution preparation (11.9.6)

The manual Windows workflow validates a tagged source without signing secrets, then allows a separately gated release job to sign, verify and publish the NSIS installer plus alpha metadata. It has **not been run as a release**. The installer name, executable name and x64 target are now explicit; source and generated artifacts have fail-closed guards. See [Windows Alpha Distribution](WINDOWS_ALPHA_DISTRIBUTION.md) for required environment protection, secret names, release assets, tester instructions and the single accumulated Windows smoke checklist. The Desktop Preview is not yet ready for testers.

## Development

From the repository root, run `npm ci`, then `npm run check --workspace @cubic/desktop`, `npm test --workspace @cubic/desktop`, and `npm run build --workspace @cubic/desktop`. These run without a GUI. `npm run desktop:dev` launches Electron only on a machine with a GUI and network access to the production Cubic site. This build compiles TypeScript; it does not produce an installer. `npm run package:win --workspace @cubic/desktop` is reserved for an appropriately signed Windows release environment and never publishes by itself.
